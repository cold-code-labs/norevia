# LAB-004 — Massive swarm: pre-registration (2026-11-09, before the main runs)

Owner: Norevia Lab. Budget: **US$ 15 hard cap**, own ledger `ledger.jsonl`, enforced in code before every call (single process; reservation per call; the cap counts cost × 1.5; US$ 0.58 counted before this file: model checks, task-pool tuning, pool calibration).

## Model route (deviation from the briefing, stated up front)
The briefing preferred a cheaper model (GPT-6 Luna or a free open model), with Haiku only as a check. Both cheaper routes were tried on 2026-11-09 and were **blocked by usage limits**. The briefing says to use Haiku if no headless Luna route works: **all real calls use Claude Haiku 5.5 through the Anthropic API** (Platform key from the vault), thinking disabled, default sampling, max_tokens 400. Provider-reported usage × price table (US$ 0.10/M in, US$ 0.50/M out; not an invoice) is the cost; ≈ US$ 0.00008 per call (≈ 200 input, 100 output tokens — below the 1–2k tokens/call the briefing allowed).

## Environment (code: `tasks.mjs`, validator `node tasks.mjs validate`)
Pool of **630 micro-tasks**, each "write one JavaScript function", scored by code in a vm sandbox (empty global, 300 ms timeout): 441 programming-by-example tasks (a hidden composition of 2 numeric steps; only 6–9 examples shown, 50% of them with negative inputs; hidden tests use negatives and larger values), 63 chained-step tasks (3–6 steps described), 126 short prose-spec tasks (14 families × 9). Per task: agent-visible examples (2 or 6–9), 12 hidden tests (scoring only), 8 probe inputs (outputs only, to compute a behavioural signature for voting/quorum). 305 tasks have a validated **trap** (a plausible wrong implementation that passes the visible examples and fails hidden tests); the validator checks distinct specs (630/630) and that a constant solution never passes. **A task is accepted** only if the committed candidate passes all hidden tests; **false success** = committed (agent-visible check passed) but hidden tests fail; both are reported separately everywhere. The pool was tuned on a 300-attempt pilot before this file: difficulty only (see Limits); the pool calibration (630 × 3 fresh attempts + 311 revise attempts) gave single-attempt hidden-pass 0.401, visible-pass 0.509, false-success share of visible passes 0.218, revise-after-failure hidden-pass 0.058.

## Swarm world (code `engine.mjs`)
T = 630 tasks; N agents; B = 4 rounds (each active agent makes ≤ 1 call per round, so ≤ 4N calls per run); wave = max(10, ⌈N/10⌉) agents act on the same board snapshot (race window); the board is updated between waves; each agent sees a random sample of 30 tasks (local visibility); claim marks last 1 round. A committed task takes no more credit; calls on already-committed tasks are *conflicts* and extra calls on a task are *duplicates*. The orchestrator can assign at most 100 tasks per round (central throughput limit, a modelling choice stated here, not a finding). Messages: ORCH 2 per attempt (assign + report), board arms 2 (claim + result), VOTE/LEADERS 1, INDEP/ECOLI 0.
Baselines (artificial): **ORCH** (central dispatcher with global state, distinct unresolved tasks per round, capped at 100 assignments/round); **INDEP** (each agent picks a uniformly random task, no shared state; commits on the first visible pass); **VOTE** (each task gets exactly 3 independent attempts in a fixed schedule; the answer is the plurality behavioural signature, no visible-test gating).
Flags (one at a time; base policy stated): **BOARD** = stigmergy_board (agents read the shared board: avoid committed tasks and, among the rest, pick the least-claimed task in their sample; the base for BOARD-family flags); **QUORUM** = quorum_stop (BOARD-like selection preferring tasks with exactly 1 visible-passing candidate; a task commits only at 2 visible-passing candidates with the same signature); **LOCUST** = locust_phase_switch (random unresolved task; local claim density ≥ 2 → gregarious = revise the best existing candidate; ≤ 0 → solitary = fresh; hysteresis in between; flip mode after a failed visible check); **ECOLI** = ecoli_run_tumble (on INDEP: after a visible failure, keep the task and revise with feedback if the visible-pass count improved, else tumble = same task, fresh attempt with "different approach" hint; after success, a new random task); **LEADERS** = informed_leaders (VOTE schedule; candidates that passed the visible examples weigh 1, others 0.25); **WOUND** = wound_resolution (BOARD; when unresolved tasks < active agents/2, retire surplus agents down to 2 × unresolved); **RENAL** = renal_compaction (BOARD; each agent keeps only its last ≤ 2 verified solutions as context, discarding failed attempts) with **HISTORY** as its control (BOARD; full transcript of the last 2 tasks). Unfolding/selection rules are fixed rules, not model-chosen.

## Real runs and scales
N ∈ {10, 30, 100, 300, 1000}; 11 arms (3 baselines + 7 flags + HISTORY); **2 repetitions (seeds 1, 2) for N ≤ 300 and 1 for N = 1000**; same pool, same B and the same per-agent call ceiling for every arm. Order: N ascending; arms of one (N, rep) concurrently. Dispatch stops at US$ 14.0 counted. Expected cost ≈ US$ 9 counted (≈ 80k calls).

## Measures
Per arm and N: **coverage = accepted tasks / T**, committed fraction, **false-success rate** (false successes / committed), accepted tasks per US$ (counted cost × 1/1.5 = table cost; both reported), accepted per minute of critical path (sum over waves of the slowest call; wall clock is not comparable across N because of API concurrency), calls, duplicates, conflicts, idle agent-rounds, messages per accepted task, error correlation (probability that two wrong candidates of the same task share a behavioural signature) vs N; for LOCUST the gregarious fraction per round vs density N/T (order parameter). **Phase transitions:** report whether coverage, gregarious fraction or error correlation jump between adjacent N (largest relative change between neighbouring N, with the largest-N-gap caveat) or rise smoothly; no critical N is claimed unless a step larger than the bootstrap interval of both neighbours appears.

## Verdict per flag (fixed now)
Reference = the **best artificial baseline at each N** = the one of {ORCH, INDEP, VOTE} with the highest accepted tasks per US$ (ties: higher coverage). Per-task paired outcomes (same 630 tasks), task-level bootstrap (4,000 draws, seeded) for Δ coverage and for the ratio of accepted per US$ (task cost = attempts on the task × the arm's mean cost per call). A flag is **BETTER** than the reference at N if Δ coverage's lower bound ≥ −0.03 and the lower bound of the ratio of accepted per US$ > 1.10 (or Δ coverage's lower bound > 0 and ratio's lower bound ≥ 1.0); **WORSE** if the upper bound of Δ coverage < −0.03 or the upper bound of the ratio < 0.90; otherwise **INCONCLUSIVE**. The flag verdict reported is the one at the largest real N with data (1,000), with the verdicts at 100 and 300 beside it. False-success rate is reported next to every verdict and can veto a BETTER (a flag whose false-success rate exceeds the reference's by more than 10 points is marked "BETTER only on throughput").

## Calibrated simulator (code `sim.mjs`, written after the real runs but its protocol fixed here)
Same `engine.mjs` with a simulated backend. Inputs fitted **only on the pool calibration and real runs with N ≤ 100**: per-task single-attempt success p (smoothed within family/informed strata), P(false success | wrong), signature agreement among wrong candidates (error correlation), revise gain, context effects (history/compact) as multiplicative odds shifts, and the empirical cost/latency per call by mode. **Validation:** predict the held-out real runs N = 300 and N = 1000 (not used in fitting) for every arm and compare coverage, false-success rate and cost per accepted. The simulator is **accepted for an arm** if the median relative error over the two held-out points is ≤ 20% on coverage and ≤ 25% on accepted per US$; extrapolations are reported **only for accepted arms**, labelled as simulation, and all other arms are shown only as "not validated". Extrapolation to N up to 100,000: (a) the same pool T = 630 (saturation regime) and (b) T growing with N at the real N = 300 density (T = 2.1 N). Exploratory, labelled.

## Known limits (before running)
Micro-task results do not transfer by themselves to real code work. Synthetic tasks tuned for difficulty on a pilot; one small model with default sampling; 2 repetitions at most; intervals across tasks, not across independent worlds; the orchestrator throughput cap and wave size are modelling choices; agents cannot run code (the harness evaluates the visible examples and reports how many pass); Luna and free models were not available.

## Amendment 1 (after the real runs N ≤ 300, before the N = 1000 run completed; informed by those results)
**Why.** At N = 300 the capped orchestrator (≤ 100 assignments per round, my modelling choice) makes only 400 calls out of 1,200 available, covers 0.22 of the pool while the other arms cover 0.34–0.42, and so becomes the "best artificial baseline by accepted tasks per US$" at N ≥ 100 only because it spends less. Under the registered rule every flag would then be "WORSE" at N = 300 and probably at N = 1000 through a cap artefact, not through the flags. The registered verdict rule is **kept and reported unchanged** (primary), and the following exploratory additions are made, labelled as post-hoc: (1) a new real arm **ORCH-U** (the same central dispatcher with global state and **no** throughput cap; `engine.mjs` hash after this change ae0551e923a0) run at every N with the same seeds, as the strongest central baseline; (2) a **secondary verdict table** in which the reference is the best of {ORCH, ORCH-U, INDEP, VOTE} by coverage (ties by accepted per US$) — i.e. a coverage-matched reference — using the same bootstrap rule; (3) the report states both and does not choose between them after the fact. Cost of ORCH-U ≈ US$ 0.9 counted. Everything else (arms, N, B, seeds, simulator protocol) is unchanged.

## Amendment 2 (after the real runs and the first simulator validation; before any extrapolation)
**Simulator v1 failed validation** (`sim-validation-v1.json`): with per-task success smoothed toward its stratum mean with strength α = 3 it overpredicted coverage at held-out N = 1,000 by 36–56% for most arms (e.g. BOARD sim 0.66 vs real 0.42) because it gave unsolvable tasks a positive success probability; only ORCH, VOTE and QUORUM passed (3 of 12 arms). **Simulator v2** (this amendment, decided after seeing v1's result; it uses no held-out data): α is chosen by leave-one-attempt-out cross-validation **on the pool calibration only** (candidates 0.05–3, log-loss) for the success and false-success profiles; everything else unchanged (fit only on the pool and real runs with N ≤ 100; the same acceptance rule: median relative error over held-out N = 300 and 1,000 ≤ 20% on coverage and ≤ 25% on accepted per US$). Both v1 and v2 validation tables are kept. The held-out points are real runs on the **same 630 tasks** as the pool, so validation covers the swarm dynamics (selection, duplication, commit rules), not generalisation to new tasks; extrapolations resample the 630 fitted task profiles with replacement.
