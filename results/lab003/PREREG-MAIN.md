# LAB-003 — Main pre-registration (2026-11-09, before Q1–Q3 main runs)

Budget: US$ 15 hard cap, one ledger for all of LAB-003 (`ledger.jsonl`; the cap counts cost × 1.5; US$ 2.64 counted before this file: API checks, Step 0 calibration, three smoke runs). Model `claude-haiku-5-5` via the Anthropic API, default sampling, max_tokens 64,000 per call. Step 0 gate **passed** (`PREREG-STEP0.md`, `calibration-cal.json`, `calibration-cal2.json`): with the 0.6 probe, probe-pass → hidden-fail was 0/76 (k = 1) and 0/17 (k ≥ 3, Wilson upper bound 0.18) after repair, against 6/10 on first-pass candidates under the visible-only probe. Probe share fixed at 0.6; acceptance = full hidden suite; false success reported everywhere as a separate outcome. Smoke runs only checked that the code runs; they informed no parameter.

## Shared definitions
Task = repository of k packages from the 38 validated Observatory packages. Agent-visible probe per package = visible tests + 60% of hidden cases (the unseen cases are never in any prompt). Accepted = every hidden test passes. Cost = tokens × price table (US$ 0.10/M in, 0.50/M out; not an invoice). Per-run ceilings, identical for every arm of a question: calls ≤ 2k+4 and USD ≤ 0.02 + 0.00006 × LOC (Q1); Q2 extra budget fixed below; Q3 as Q1. Resampling unit = task (all its repetitions together), 4,000 seeded bootstrap draws; Wilson for rates. "n" is small everywhere (budget); intervals are wide by design of the budget, and verdict rules below say what counts.
Order and stopping: repetition by repetition across Q1, Q2, Q3 (rep 1 of all three, then rep 2, then rep 3) so budget shortfalls cut all questions equally; dispatch stops when the counted ledger reaches US$ 14.0; only complete repetitions are analysed.

## Q1 — When does splitting pay?
Tasks (fixed, seed 77, `plan.mjs`): 6 of 1 package, 4 of 3, 3 of 8, 2 of 15 (≈ 15 is the largest that fits comfortably; sizes 1, 3, 8, 15). 3 repetitions. Arms: **SOLO** (one agent on the whole repository, ≤ 2 probe repairs, a repair kept only if the probe pass count does not drop) vs **TEAM** (one owner per package with package-only context, in parallel; then up to 2 repair rounds only for packages whose probe still fails; no patrol). One variable: split or not.
Outcomes: primary = cost per accepted task at each k (task level) with acceptance and false success; secondary = cost per accepted package, hidden-pass fraction, truncated calls (output hit the 64k cap), calls.
**Crossover**: ρ_k = cost per accepted (TEAM) / cost per accepted (SOLO) at each k. TEAM "pays" at k if the upper 95% bound of ρ_k < 1 (if SOLO accepts nothing at k and TEAM accepts something, TEAM pays). Crossover k\* = exp(−a/b) from the least-squares line log ρ = a + b·log k over the four sizes, with a 95% bootstrap interval (tasks resampled within each k); if b ≥ 0 or the line never crosses 1 within 1–15, report "no crossover in 1–15". Also report the smallest tested k where TEAM pays.

## Q2 — Retry or recruit?
Tasks (fixed, seed 88): 6 tasks of 8 packages, 3 repetitions. Stage 1 (shared by all arms, so comparisons are paired on the same state): one fresh owner per package, package-only context, accepted per package if the probe count does not drop; no repair. Then each arm spends **exactly E = k = 8 extra calls**: **RETRY** (the same owner re-reviews its own previous answer given its probe feedback; one call per package); **RECRUIT-U** (fresh agents that see only the current code and feedback, uniform: one per package); **RECRUIT-T** (fresh agents allocated by response threshold: stimulus s = max(0.15, failing-probe fraction); ladder θ ∈ {0.1, 0.3, 0.5, 0.7, 0.9}; a package gets one recruit per θ below s, then trimmed or filled to E by stimulus; several recruits on a package are independent candidates, best by probe kept). **NONE** = stage 1 only (reference). One variable per contrast: RETRY vs RECRUIT-U isolates "fresh agent vs same agent"; RECRUIT-U vs RECRUIT-T isolates "allocation by threshold"; RETRY vs RECRUIT-T is the contrast the question asks for.
Outcomes: task acceptance and package acceptance rate (primary: acceptance difference with 95% bootstrap interval; cost per accepted task, which includes stage 1, as the second reading). Verdict rule: a contrast is **BETTER** if the lower bound of Δ task acceptance is ≥ −0.10 and cost ratio ≤ 0.80 with upper bound < 1, or lower bound of Δ acceptance > 0 and ratio ≤ 1.25; **WORSE** if the upper bound of Δ < 0; otherwise INCONCLUSIVE (same rule as LAB-001). Interpretation fixed now: if RECRUIT-T does not beat RETRY, the LAB-001 THRESH gain is "more attempts", not a swarm mechanism; if RECRUIT-U also beats RETRY, freshness (independent attempts) explains it; if RECRUIT-T beats RECRUIT-U, allocation by stimulus adds something.

## Q3 — Does request-type memory help?
Sequence (per repetition, seed 1000 + rep): all 38 single-package requests in a seeded shuffled order (≥ 20 required), 3 repetitions (3 different orders), run twice from an empty memory: **NOMEM** and **MEM**. Request type = package class (b independent kit; c coupled system). MEM: after a request whose final probe passes, one distillation call writes ≤ 3 generic lessons (≤ 160 chars); lessons are kept per type, bounded to 1,200 characters (oldest dropped), and shown to later requests of the same type; distillation cost is charged to MEM. One variable: memory on/off.
Outcomes: **first-pass failure rate** (the first attempt, before any probe feedback, fails the probe) and **cost per accepted task**, with Wilson intervals and a paired bootstrap of the difference over (rep, position) units; also hidden failure of the first attempt, and the second half of each sequence (positions 20–38) where memory has had time to build. Verdict: **helps** if the upper bound of Δ first-pass failure (MEM − NOMEM) < 0 and the upper bound of the cost ratio ≤ 1.10; **harms** if the lower bound of Δ > 0; otherwise no detectable effect. LAB-002's exploratory 4/4 is "confirmed" only if this rule says helps.

## Known limits (stated before running)
Single-package packages are near the ceiling for one agent (calibration: 76/76 accepted after repair; first-pass failure ≈ 18%), so Q3 has little room and low power; Q1 at k = 1 is equal by construction and is a functional check, not a result; tasks reuse the same 38 packages (not independent; resampling by task); one small model; probe leakage of 60% of hidden cases is by design; cost from a price table; 2 tasks only at k = 15.

## Amendment 1 (after Q1–Q3 repetition 1 and the start of repetition 2; before any Q2b run) — Q2b: Q2 in a harder regime
Why: in repetition 1 of Q2 every arm that spent the extra calls reached 6/6 accepted tasks (NONE 3/6): with the strengthened probe and E = k = 8 extra calls, any additional attempt repairs everything, so Q2 cannot tell retry from recruit (ceiling). This is reported as a result of Q2 (probe feedback plus any extra attempt suffices at this difficulty and budget), and a tighter regime is added; it was chosen after seeing that ceiling, not after seeing any Q2b outcome.
Design (code `q2b.mjs`, sha256 66553f5e4180, differs from `q2.mjs` only in tasks, E and allocation): 6 tasks of 8 packages = **5 "hard" + 3 other** packages (hard = the 9 packages with ≥ 1 first-pass probe failure in the k = 1 calibration: agenda-kit, codecs-kit, calendar-kit, grafos-kit, texto-largura, protocolo-quadros, calendario-fiscal, numeros-kit, recorrencia-agenda; seeded draws 9100+i / 9200+i), 3 repetitions, **E = 4 extra calls**, same stage 1 and same arms (NONE, RETRY, RECRUIT-U, RECRUIT-T). To avoid a strawman at E < k, RETRY and RECRUIT-U allocate their calls need-ordered (failing packages first, most failing tests first, round-robin; if none fails, packages in order); RECRUIT-T allocates by response threshold (unchanged). Outcomes, contrasts and verdict rules are exactly those of Q2. Q2b results are reported next to Q2 and are the primary evidence for the Q2 answer when Q2 is at the ceiling. Estimated cost ≈ US$ 2.3 counted; the US$ 14.0 stop line still applies.

## Amendment 2 (budget reality; before any Q2b outcome was seen)
The ledger stood at US$ 12.37 counted with Q1–Q3 repetition 3 and Q2b rep 1 just started: Q2 costs ≈ US$ 1.5 counted per repetition (my estimate was 0.9), so the US$ 15 cap cannot fund 3 repetitions of everything. Decisions: (1) **Q2 repetition 3 cancelled** (process stopped; its completed task-units stay in `runs-q2.jsonl` but are excluded because the repetition is incomplete); Q2 rests on repetitions 1–2 and is at the ceiling. (2) **Q2b runs 1 repetition** (6 task-units, est. ≈ US$ 1.0) instead of 3, so its intervals will be very wide; it is exploratory evidence. (3) Q1 and Q3 repetition 3 continue (only complete repetitions analysed). (4) The US$ 14.0 dispatch stop line and the US$ 15 hard cap are unchanged; no further experiment is added.
