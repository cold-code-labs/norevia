## Mechanism

1. **Communication topology.** Two processes: `Process.sequential` and `Process.hierarchical` (`process.py:L4-L10`; `consensual` is only a TODO at `L11`) **[code]**. Default `process=Process.sequential` (`crew.py:L256`) **[code]**. In sequential, tasks run in a `for` loop in list order; the context passed to each task is, by default, the concatenation of the previous outputs (`crew.py:L1601-L1646`; `_get_context` at `L1887-L1895`) **[code]**. Tasks with `async_execution` become futures and are gathered before the next synchronous one (`crew.py:L1616-L1631`) **[code]**. In hierarchical, all tasks are assigned to the manager (`_get_agent_to_use`, `crew.py:L1733-L1736`), which talks to the workers via delegation tools → star **[code]**.
2. **Who decides who acts.** Sequential: the order is fixed by the developer (each `task.agent`) **[code]**. Hierarchical: the manager's LLM chooses the "coworker" via `DelegateWorkTool`/`AskQuestionTool` (`crew.py:L1533-L1566`, manager created with `tools=AgentTools(agents=self.agents).tools()` at `L1556`) **[code]**. Each delegation creates a new `Task` for the chosen agent and calls `execute_task` (`tools/agent_tools/base_agent_tools.py:L110-L119`) **[code]**. If the task already has an assigned agent, the manager can only delegate to it (`crew.py:L1878-L1879`) **[code]**. In a sequential process, agents with `allow_delegation=True` (default `False`, `agents/agent_builder/base_agent.py:L278-L281`) get tools to delegate to the others (`crew.py:L1839-L1849`) **[code]**.
3. **Termination criterion.** The crew terminates at the end of the task list (`crew.py:L1601-L1646`) **[code]**. Per agent/task: `max_iter: int = 25` (`agents/agent_builder/base_agent.py:L285-L287`); when reached, the executor **forces a final answer** with one more LLM call instead of aborting (`agents/agent_executor.py:L2519-L2531`; `utilities/agent_utils.py:L374-L385`, `L387-L441`) **[code]**. It also forces a final answer after 5 consecutive identical tool calls (`MAX_REPEATED_TOOL_CALLS = 5`, `utilities/agent_utils.py:L1996`, `L2097-L2099`) **[code]**. `max_execution_time: int | None = None` (`agent/core.py:L268-L271`) raises `TimeoutError` without retry (`agent/core.py:L1026-L1042`, `L1077-L1080`) **[code]**. Flow-executor safeguard: `max_method_calls = max_iter * 10` → `RecursionError` (`agents/agent_executor.py:L278`; `flow/runtime/__init__.py:L3379-L3386`) **[code]**.
4. **Mechanical verification/acceptance.** **Task guardrails**: `guardrail`/`guardrails` accept a function (deterministic, user code) or a string (converted into `LLMGuardrail`, LLM-judge) (`task.py:L262-L283`, `L401-L417`; `tasks/llm_guardrail.py:L49`, `L93`) **[code]**. Failure → re-executes the task with the error as context, up to `guardrail_max_retries: int = 3` (`task.py:L289-L291`, `L1411`, `L1466-L1482`); exhausted → `Exception("Task failed ... validation after N retries")` (`task.py:L1450-L1459`) **[code]**. `HallucinationGuardrail` is a placeholder that always approves in the OSS version ("Premium hallucination detection skipped", `tasks/hallucination_guardrail.py:L20-L21`, `L97-L102`) **[code]**. **Schema** (`output_pydantic`/`output_json`): conversion uses a converter LLM with up to `max_attempts=3` (`agents/agent_builder/utilities/base_output_converter.py:L31-L34`; `utilities/converter.py:L110-L123`), but, if it fails, it **falls back to the raw string with a warning** (`utilities/converter.py:L424-L431`) and `pydantic`/`json_dict` remain `None` (`task.py:L1301-L1315`) — non-blocking validation **[code]**. `crew.test()` uses an LLM evaluator agent with a 1–10 score (`crew.py:L2344`; `utilities/evaluators/crew_evaluator_handler.py:L59-L75`) — LLM-judge **[code]**.

## Engineering analogue

*Engineering hypothesis.* In the Swarm Efficiency Observatory, CrewAI offers the cleanest "fixed sequential vs hierarchical with manager" pair over the same agents, and **code** task guardrails can serve as verifiable acceptance (running the task's tests). Beware of two cost biases: (a) the guardrail retry re-executes the entire task (up to 3 times) — cost per accepted task must account for failed attempts; (b) reaching `max_iter` does not abort, it generates an extra call to force an answer. A hard budget would have to be external (LLM hook or wrapper over `UsageMetrics`).

## Testable hypothesis

- H1: With the same agents and a code guardrail (tests), `Process.hierarchical` consumes ≥ 1.5× the tokens per accepted task of `Process.sequential` in 3-task pipelines with known order, with no acceptance gain > 3 p.p. Metric: `UsageMetrics.total_tokens` / accepted tasks.
- H2: Replacing a string guardrail (LLMGuardrail) with an equivalent code guardrail reduces false acceptances (outputs that fail the tests) by ≥ 50% and reduces the mean cost per accepted task, despite more retries.
